# AGENTS.md

This file gives guidance to AI coding agents (Claude Code and others) that work in this repository. `CLAUDE.md` only imports this file, so keep all project guidance here.

## The project

Robot Chess is a 3D chess game for kids and teens that runs in the browser. You play real chess against a Stockfish bot or against a friend on the same device, a coach explains every move, and the pieces are friendly robots built and animated in code with three.js. It is a static website with no server. `robot_chess.md` is the design brief and `README.md` is the overview for people.

Graphics are the top goal. The user said the look must make people say "WOW", and this wins over the brief where the brief calls the coach the main selling point. When you trade effort between features and visuals, favor visuals. Keep new art in the same style: low-poly nature built in code, and glossy toy robots with cyan (white team) and orange (black team) lights.

The defaults are deliberate user choices, not leftovers: the Meadow board theme (a floating garden island) and the Blue board colors. The user picked Blue because white robots were hard to see on near-white tiles.

Two more choices are deliberate, because bright white areas and glowing lines made the user's eyes tired. The white team's shell is a warm ivory, not pure white. The Meadow board has no light under its tiles (`lights.seam` is 0 in `src/gfx/palette.js`), so only its border strips and four corner lamps glow; Twilight and Galaxy keep that light. The user also compared orange, gold, blue and a darker cyan for the white team's lights and chose to keep the bright cyan, so do not make it weaker or change its color without asking.

Two starting values in the settings are deliberate too. The coach starts on Middle (level 2), because the user found the Beginner coach less helpful; only a player who answers "I play often" at the first start begins on Advanced, with the evaluation bar. "Ask before each move" is off for every player. No onboarding answer may turn on the Beginner coach or the confirm step: the player picks them in the settings. The one number for the coach is `DEFAULT_LEVEL` in `src/coach/levels.js`, which `SCHEMA` and `onboardingDefaults` in `src/core/settings.js` both use. A save that already holds Beginner or the confirm step keeps it, so never add a step that rewrites saved values to the new defaults.

The first start asks one question only: how well the player knows chess. The user had the age question removed, because it changed the starting values in only one case out of nine, so do not ask for the age again. The answer sets the starting bot level and coach level through `onboardingDefaults` and is then dropped: it is not a setting, because nothing reads it later. A coach level follows chess understanding, not age.

## Commands

```bash
npm install                                 # also copies the Stockfish files into public/engine/, writes public/licenses.txt and draws the app icons into public/icons/ (postinstall)
npm run dev                                 # dev server on http://127.0.0.1:5173
npm test                                    # all unit tests (vitest run)
npx vitest run tests/coach/report.test.js   # one test file
npx vitest run -t "parseInfoLine"           # tests whose name matches
npx vitest                                  # watch mode
npm run build                               # static site in dist/
npm run preview                             # serve dist/ locally
npm run engine:copy                         # copy the engine again if public/engine/ is missing
npm run openings:build                      # rebuild public/data/openings.json from the Lichess dataset (needs network)
npm run licenses:build                      # write public/licenses.txt again
npm run icons:build                         # draw the app icons again
```

There is no linter or formatter in this project. Match the style of the code around your change.

## Git workflow

This is a normal GitHub project. Keep `origin` pointing to `git@github.com:alsatianco/robot-chess.git` and use the usual branch and pull request workflow when needed. Do not remove the remote or change its URL unless the user asks. Do not run `git push` unless the user explicitly asks. Keep the git author that is set in this repo's `.git/config`.

After every meaningful change, make a commit. A meaningful change is one finished step that works on its own: a feature, a fix, a tuning pass, a refactor or a doc update. Before you commit, run `npm test` and make sure it passes. If you changed something visual, check it on screen first (see "Checking visuals"). Do not commit a broken state.

The commit message is one line only: short, in the imperative mood, with no body and no trailers (no `Co-Authored-By` line). Examples: `Add board colors setting with Blue as default`, `Fix bot clock running while a move animates`. Stage the files you changed by name and check `git status` before you commit.

## Architecture

The big ideas below each span several files. Read the one-line header comment at the top of any file to see what it does.

**Start-up and wiring.** `src/main.js` builds every system, connects them and runs the frame loop. The board is drawn first and the engine loads in the background after the first frame. `applySetting` in `main.js` is the one place that maps each setting to the system it changes. The frame loop draws at most at the player's frame-rate limit (`FrameLimiter` in `src/app/frame-limiter.js`: 30, 60 by default, or max), and it lowers the graphics quality by itself when the frame rate stays low and the quality setting is "auto" (the watchdog). The "too slow" threshold follows the limit (`slowFrameRate`), so a game held at 30 on purpose is not called slow.

**Auto graphics quality measures the device, it does not guess.** A browser does not say how strong the graphics chip is: Safari tells no memory size and only "4 or 8" processor cores (on iPhone, iPad and Mac alike), Firefox tells no memory size, and Chrome tells it only on https pages. An earlier rule read these numbers and counted a missing one as a weak device, so every iPhone and iPad started on Low; the user found this on an iPad that runs High well. So `src/app/auto-quality.js` measures: in the first frame, still under the loading screen, `measureQuality` in `main.js` draws real frames one after the other, waits for the graphics chip (`Stage.waitForGpu`, a read of one pixel) and takes the time. `pickQuality` starts at a first guess (`guessQuality`, which never counts a number that the browser does not tell against the device), goes down while a level is too slow and tries the next level up while the forecast says that it can fit. A level is kept when the device draws it at about 32 frames per second or more (`KEEP_FRAME_MS`): the look comes first, and the limit sits a little above the watchdog's "slow". A graphics chip that was idle runs slowly at first, so each level is drawn for at least 0.3 seconds and the fastest sample counts. The result is kept in the browser's storage (`QualityMemory`, key `robot-chess.quality.v1`) with the pixel count of the picture, so a device is measured once; a much bigger or smaller window is measured again. Picking "Auto" in the settings measures again, and a step down by the watchdog is remembered too. The settings show the level that Auto uses. The page stands still while it measures (about a third of a second for each level), so never measure during play.

**The game owns the state, the view only shows it.** `Game` (`src/core/game.js`) holds the real chess state through chess.js and decides everything: turns, the modes (`MODES`), clocks, undo, coach and game end. A move is committed in `Game` the moment it is made; the animation is only a picture. `BoardView` (`src/gfx/boardview.js`) shows the state and puts every robot back on its real square after each animation, so the picture can never drift away from the game. The UI listens to `Game` events (`change`, `gameover`, `toast`).

**Saved game.** A game in progress is written to the browser's storage after every move, and once more when the page goes to the background (`GameSaver` in `src/core/saved-game.js`, key `robot-chess.game.v1`). `Game.snapshot()` gives the data and `Game.resume(saved)` puts a game back; `checkSavedGame` checks every field and replays the moves, so a damaged save is dropped and never breaks the game. The home menu then offers "Continue your game". Leaving a running game with the Home button gives it up (the player is asked first), and a new game takes the place of a saved one. Saves under this key must stay loadable, like the settings.

**Async work and the epoch.** `Game.epoch` goes up whenever a game is replaced, rewound or ended. Every async step saves the epoch before it waits and stops if the epoch changed. Keep this pattern in any new async code in `Game`, or old animations and engine replies will act on a new game.

**Clock and timing rules.** `ChessClock` runs only when `Game` starts it, so an animation never costs clock time. The bot thinks while the player's move animates, and its clock pauses as soon as its move is found. In Coach mode the engine analyzes the player's position while the bot's move animates, so feedback adds no waiting. The bot holds its reply while the coach is still working (`coachPending`) or while a flagged move waits for the player (`coachHold`). When the player answers "Keep going" for a piece in danger, `Game.acceptedDangers` remembers that danger, so the coach does not stop the game a second time for the same piece while the danger stands.

**Two players.** The mode `two` in `MODES` is a game between two people at one device. It has no bot (`bot: false`), and its clock and its coach say `'choice'` instead of yes or no: the players pick the clock in the menu and switch the coach on in the settings. So never test `mode.clock` or `mode.coach` as a plain yes or no. Ask `modeHasClock` for a setup, and `game.clock` and `game.coachOn` for a running game. `playerColor` and `botLevel` mean nothing in this mode, so check `mode.bot` before you use them. After each move `Game` calls `turnBoard` (passed in by `main.js`) and waits for it before the next player may move and the next clock starts, so the flip of the board costs no clock time, like every other animation. With the coach on, the board stays with the player who moved until that player has answered a flagged move, and the coach remembers accepted dangers for each color apart. `Game.applyCoachSetting` makes the coach switch work in the middle of a game. `Game` emits `start` whenever a game is set up (a new one, "Play again", a saved one that goes on), and `main.js` sets the side of the board there, so do not set it anywhere else. In the interface the player bars follow the side of the board (`AppUI.setOrientation`). The starting values are the user's choices and follow the pass-and-play modes of other chess apps: the board flips after each move, the coach is off and there is no clock. Both switches are in the settings group "Two players".

**Engine.** `Engine` (`src/engine/engine.js`) wraps the single-threaded Stockfish build in a Web Worker. It runs one search at a time and queues the rest. `Game` uses two engines, one for the bot and one for the coach. A two-player game without the coach uses no engine at all, so it also works where the engine can not start. Bot levels 1 to 3 pick from ranked moves with randomness; levels 4 to 8 use Stockfish's skill setting (`BOT_LEVELS` in `src/engine/bot.js`). The ladder follows the computer levels of Lichess, and levels 4 to 7 use the ratings that the Stockfish team published for its skill levels; the sources are in the comment above `BOT_LEVELS`. Take strength numbers from published sources like these, not from your own engine matches. Use only the single-threaded build: the multi-threaded one needs COOP/COEP headers that many static hosts cannot set.

**Coach pipeline: detection is kept apart from presentation.** `report.js` builds the facts for one move (rating, best and equal moves, material outcome, findings from `detectors.js`). `levels.js` is pure data: a level is only limits and switches, and the detectors do not know about levels. `present.js` turns a report into text, faces, stars, highlights, arrows and ghost lines, and takes all words from the translator. `illegal.js` explains why a move is illegal, because chess.js only says that it is. The coach code has no DOM and no three.js, so it runs in tests. All tuning numbers are in `src/coach/constants.js`.

**Graphics.** `Stage` (`src/gfx/stage.js`) is the render pipeline: renderer, bloom and other post effects, and the `QUALITY` levels. Most GPU time goes to full-screen work at screen resolution (a retina-size HDR image with 4x MSAA), not to the 3D shapes, so the pipeline keeps full-screen passes to a minimum: the scene is drawn once into one multisampled HDR target, bloom only makes its glow texture (`BloomTexturePass`), and one finish pass adds the glow, applies vignette, grain and flash, and does tone mapping and sRGB on the way to the screen. Keep it that way: do not add an `EffectComposer` pass or draw a full-screen quad into a multisampled target. Anything that draws into its own target (like the floor mirror) goes in `stage.prePasses`, which run before the main pass; switching targets inside the main pass (for example from `onBeforeRender`) makes the GPU store and reload the half-drawn image. A pass whose image is only read in part should only clear, draw and resolve that part: the floor mirror sets a scissor box around the board's place on screen (`mirrorRegion` in `src/gfx/mirror-region.js`), which gives the same picture for less GPU and memory work. `Stage.render` updates the scene's matrices once per frame itself (`scene.matrixWorldAutoUpdate` is off), so always draw through `Stage.render`. `Environment` builds the world around the board ("garden" or "space") and its lights. `Arena` draws the tiles, highlights, coordinates and coach arrows. `src/gfx/palette.js` holds the team colors and the board themes; every theme defines tile colors for every board color choice (`BOARD_COLORS`). One world unit is one tile (`src/gfx/coords.js`).

**Robots.** A robot design is a tree of joints made from simple shapes (`robots/designs.js`, `robots/builder.js`). Each vertex stores a material slot number (`SLOT`), and one shader material turns the slot into the team's color and finish (`materials.js`), so both teams share the same models. All motion goes through the robot's "rig", a flat set of numbers (position, lean, squash, walk, power and so on). Clips in `anim/choreo.js` are async functions that tween rig numbers, so one clip works for all six robot types. `Animator` skips an animation by fast-forwarding time, so every tween still reaches its end value. Effects (`fx/effects.js`) are pooled and run on the same clock.

**Camera zoom.** The zoom is a factor on the distance at which the whole board just fits the free part of the screen (`fitDistance` in `src/gfx/camera-rig.js`), so the default zoom 1 (`CAMERA_LIMITS.zoomDefault`) shows the whole board on every screen size. `src/app/zoom-input.js` turns wheel, trackpad and pinch input into zoom steps from the scroll or pinch amount, never from the number of events: a trackpad sends dozens of small events per swipe, and a fixed step per event made the zoom far too fast for the user. The "Reset view" button (`actions.resetView` in `main.js`) calls `rig.resetView()`, and it is only active while `rig.isDefaultView` is false.

**Input works with a "target".** `InputController` (`src/app/input.js`) handles tap-tap and drag-and-drop and sends moves to a target. The target is either `Game` or `TutorialRunner`, and both have the same small interface: `canInteract()`, `isOwnPiece(square)`, `targetsFrom(square)` and `attemptMove(from, to, options)`.

**Settings.** `SCHEMA` in `src/core/settings.js` lists every setting with its default and a check for allowed values. Saved values are checked one by one when loaded, and a bad value falls back to its default. `set()` throws on an unknown key or a value that is not allowed. To add a setting, add it to `SCHEMA`, handle it in `applySetting` in `main.js`, add the control in `src/ui/ui.js` and add its text to `src/i18n/en.js`. Saves under the key `robot-chess.settings.v1` must stay loadable.

**Text.** All user-facing text is in `src/i18n/en.js`, and code gets it with `t('some.key', params)`. A missing key shows the key itself, so gaps are easy to see. When a value is an array, one entry is picked at random (used for varied coach lines). Use simple words: many players are young children or do not speak English as a first language.

**About screen.** The About button is the third button under Play on the home menu, and `openAbout` in `src/ui/ui.js` draws the dialog. Its addresses, profiles and credits are data in `src/ui/about.js`, and its words are under `about` in `src/i18n/en.js`. The user wants this screen humble, short and plain: it says what the game is, who it is for, where it lives and whose free work it uses. Do not add praise for the game, a feature list or a row of social profiles. Humble does not mean talking the game down: the user publishes the game only when it is ready, so do not call it unfinished or a work in progress. Kids and teens are who the game is made for, not a limit, so the text welcomes everyone, especially beginners. The last sentence links two profiles (`ABOUT_PROFILES`): the user's GitHub and an X account for news about the game. Which profiles it shows is the user's choice, so ask before you add or remove one. When you add a package to `dependencies`, add its credit too: a test fails when a shipped package has no credit, or when a credit shows a licence that the package does not declare.

**Three layouts.** `src/styles.css` picks the in-game layout from the shape of the window. A wide and tall window (a desktop, a tablet on its side) has the board on the left and a roomy column of panels on the right. An upright screen stacks the panels above and below the board. A wide window that is short or narrow (a phone on its side, a small browser window) keeps the board on the left and puts everything else into one slim column. The panels whose size changes during a game (the coach card or lesson card, the move list, the action buttons) are in the dock (`.dock`, built in `src/ui/ui.js`). On phones the move list is hidden during a coach game and comes back when the game is over, and the action buttons are hidden while the coach waits for an answer (the classes `is-over` and `is-hold`).

**Installable app and play with no internet.** `public/manifest.webmanifest` holds the name, colors and icons of the installed app; the icons are drawn in code by `scripts/build-icons.mjs` into `public/icons/` (git-ignored). The service worker (`src/pwa/service-worker.js`) keeps every file of the game on the device. It is not part of the bundle: the build writes it to `dist/sw.js` with the list of built files in it (the `writeServiceWorker` plugin in `vite.config.js`, with `scripts/build-service-worker.mjs`), and `src/pwa/register.js` starts it two seconds after the first frame, in the built site only. `InstallPrompt` (`src/app/install.js`) decides when the game may offer "Install", and the home menu draws a small button in its top corner (`#renderInstall` and `openInstallHelp` in `src/ui/ui.js`): Chrome and Edge open their own install dialog, and on iPhone and iPad the game shows the steps for the Home Screen. Three choices are deliberate: the offer never opens by itself, a new version takes over only after every window of the game was closed (a game in progress is never reloaded under the player), and both need https or `localhost`, while the game itself runs the same without them.

**Tutorial.** `src/tutorial/lessons.js` is data only, with i18n keys for all text. `src/tutorial/runner.js` plays the lessons on the same 3D board.

## Project rules

- No asset files: models, materials, effects and sounds are made in code. Sound uses Web Audio (`src/audio/sfx.js`). Fonts are bundled through Fontsource, so no request goes to an outside server.
- Every animation must be skippable with a tap, and long moves are a dash, glide or leap, never a slow walk. Captures are non-violent: robots power down and fall apart.
- The interface (`src/styles.css`) must not look machine-made. The user called a colored stripe on one side of a box "AI style" and had all of them removed. Do not give a box a thick border on one side or a blurred glow ring. Show a state with the whole outline of the box: the bar of the side to move takes its team's light color, and its team dot lights up. Do not color a box for a fact that something else already shows: the team dot shows the team, and the robot face and the rating badge show the coach's mood. Buttons in a group have the same width in every row, so the gaps line up.
- The board stays where it is. Only the player may change the board's place and size on screen (zoom, turn, top view, the window). The user tested on a phone where the coach card grew after each move, the board area got smaller and the camera zoomed out and back: hard on the eyes, and a tap can land on the wrong square. So the box of the board area (`ui.boardArea`) may depend only on the size of the window and on real switches of the screen (menu, game, tutorial, coach on or off), never on what a panel says. A panel whose text changes gets a room of a fixed size, grows downward and scrolls inside: on upright screens this is the dock, which has a height of its own (see "An upright screen" in `src/styles.css`). In dev mode `main.js` prints a `[layout]` warning when the board area changes without such a reason.
- Each source file starts with a one-line header comment that says what the file does. Comments are written in simple English as one long line and are never hard-wrapped.
- Code is plain JavaScript ES modules with JSDoc types (no TypeScript). Private methods use `#name`.
- Do not hide errors. If a feature can fail (engine, opening names, storage, sound), log it with a `[module]` prefix and let the game go on without it, as `Game` does.

## Tests

Tests use vitest in a Node environment (`tests/**/*.test.js`): there is no DOM, no WebGL and no Web Worker. So the tests cover the pure logic: the game controller with a real `Game` and stand-ins for the board and the engine (`tests/core/game.test.js` and `tests/core/saved-game.test.js`, with the fakes in `tests/helpers/game-fakes.js`; this is where the two-player mode is tested), coach, clock, settings, engine output parsing and bot choice, palette tables, tutorial data, the sound module, the frame-rate limiter, the "auto" graphics quality (`tests/app/auto-quality.test.js`: the first guess for the numbers that real browsers tell, the measuring with a stand-in device and clock, the choice of the level, and the remembered record), the install offer (`tests/app/install.test.js`), the web app manifest, the service worker and its start (`tests/pwa/`), the scripts that draw the icons, write the licence file and list the built files (`tests/scripts/`), the zoom speed and the camera's default view and reset, the three.js facts that the merged bloom and finish pass depend on (`tests/gfx/stage.test.js`, which fails if a three.js update changes the stock bloom), the floor mirror's scissor box (`tests/gfx/mirror-region.test.js`, which checks it against the reading positions of the real three.js mirror code), and the links and credits of the About screen (`tests/ui/about.test.js`, which reads `package.json` and the licence of each installed package). The sound tests inject a strict fake `AudioContext` through `__setAudioContextFactory` in `src/audio/sfx.js`. The 3D scene and the UI have no unit tests; check them on screen.

## Checking visuals

Tests cannot see pixels, so check every visual change with real screenshots before you call it done.

- Game: run `npm run dev` and open http://127.0.0.1:5173/. In dev mode, `window.__app` gives you `game`, `view`, `rig`, `stage`, `settings`, `ui`, `tutorial`, `environment`, `arena`, `effects` and `input` in the console.
- Art gallery (development only, not in the build): http://127.0.0.1:5173/gallery.html with the options `?q=low|medium|high`, `?theme=meadow|twilight|nebula`, `?colors=blue|sand|classic`, `?fen=...` and `?preset=cinematic|standard|minimal`. In the console, `__gallery.play('e2e4')` animates a move and `__gallery.pause(true)` freezes time for a screenshot.
- Browser test output goes to `.playwright-mcp/`, which git ignores.
- After a change of the in-game interface, check all three layouts: a wide and tall window, an upright phone (the user's phone is about 394 pixels wide and 740 to 815 high) and a phone on its side. Play a few moves of a coach game on the upright size and read the console: a `[layout]` warning means that a panel moved the board.
- The "auto" graphics quality writes one `[quality]` line to the console with the measured time of each level. An agent has no real phone or tablet, so a slow device can only be acted out (for example with a `performance.now` that runs faster); ask the user to check on real devices.
- The home menu must fit a wide window about 790 pixels high (a small laptop) without scrolling in its usual state: a mode against the bot and no saved game. A media query in `src/styles.css` makes the menu a little tighter on such windows, and the fifth mode card is one slim line for this reason. Check this size when you add a row or a card to the menu.

## Numbers to tune by playtesting

- Bot strength: `BOT_LEVELS` in `src/engine/bot.js`. Level 1 should be beatable by a child who just finished the tutorial. Levels 1 to 3 are the game's own numbers; levels 4 to 7 follow Stockfish's published ratings.
- Move ratings and the "equal move" window: `src/coach/constants.js`. Which findings each feedback level shows: `src/coach/levels.js`.
- Animation presets: `PRESETS` in `src/gfx/boardview.js`. Graphics quality: `QUALITY` in `src/gfx/stage.js`.
- "Auto" graphics quality: `KEEP_MARGIN` in `src/app/auto-quality.js`, which sets the lowest frame rate (about 32 frames per second) at which a device keeps a quality level. It is a first value: tune it from what the user sees on real devices.
- Zoom speed: the constants in `src/app/zoom-input.js`. Zoom range and default: `CAMERA_LIMITS` in `src/gfx/camera-rig.js`.
- Two-player board flip: `BOARD_TURN_SECONDS` in `src/main.js`, the time the game waits while the camera turns the board to the next player.

## Known limits

Performance was measured only on a desktop, not on a real mid-range phone, and the "auto" graphics quality was checked on that desktop and with acted-out slow devices only. Bot levels 1 to 3 and the coach thresholds are first values, and no level is tuned with children yet. Agents check the phone layouts, the two-player mode, the install offer and play with no internet in a desktop browser at phone sizes; on real devices only the user can check them, so say what still needs the user's look.
